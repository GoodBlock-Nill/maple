New Feature · 고객지원

이메일 문의 파이프라인

푸터의 연락 이메일로 들어오는 문의를 관리자 콘솔 고객지원 › 이메일 문의에서 1:1 문의와 같은 방식으로 접수·답신·스레딩하는 기능입니다. 코드·DB·Edge Function은 모두 배포되어 있고, 메일 주소와 제공자 계정이 생기면 비밀값 설정만으로 켜집니다.

Resend · 수신 웹훅 + 발신 API Supabase · Edge Function 2개 관리자 콘솔 · 고객지원 모듈 사용자 사이트 · 변경 없음
DB마이그레이션적용됨20260909000300_email_inquiries.sql
Edge Functionemail-inbound배포됨서명 없는 요청 401 · 비밀값 없으면 503
Edge Functionemail-outbound배포됨운영자 JWT 필수 · 비밀값 없으면 503

ProviderResend 계정 · DNS · 웹훅 · secret미완§09 활성화 체크리스트
01

무엇을 만들었나

  1. 이메일로 온 문의가 관리자 콘솔 고객지원 메뉴에 1:1 문의와 같은 모양으로 쌓입니다(출처 뱃지 "이메일").
  2. 운영자가 콘솔에서 답신을 쓰면 이메일로 발송되고 같은 화면의 스레드에 "보낸 답신"으로 남습니다. 발송 상태(대기·발송됨·실패)와 "다시 보내기"가 있습니다.
  3. 사용자가 그 답신에 회신하면 같은 문의 스레드에 "받은 메일"로 붙고, 상태가 답변 완료 → 처리 중으로 되돌아옵니다.
원칙

새 인프라는 제공자 계정 하나만. 기존 1:1 문의의 테이블·화면·권한·감사 로그를 그대로 재사용합니다. 사용자 사이트 코드는 바뀐 것이 없습니다.

02

왜 이 구조인가

방식구조장점단점 · 위험
A. 제공자 수신 웹훅 (채택)메일 → 제공자 → HTTPS 웹훅 → Edge Function → DB파싱·첨부·SPF/DKIM 판정을 제공자가 해 줌. 서명 검증 하나로 인증MX 변경 또는 전달 설정 필요
B. Cloudflare Email Routing + WorkerMX → Cloudflare → Worker → 우리 함수무료, DNS가 Cloudflare면 간단MIME 파싱을 우리가 짊어짐
C. IMAP 폴링크론이 메일함을 주기적으로 읽음DNS 변경 없음메일함 비밀번호 보관, 중복·유실·파싱 전부 우리 몫. 가장 취약
D. 수동 등록운영자가 메일을 폼에 붙여 넣음개발 최소자동화 없음
  • 관리자 초대·비밀번호 재설정 메일용 커스텀 SMTP가 어차피 필요합니다. 같은 제공자(Resend)에서 수신까지 쓰면 관리할 서비스가 늘지 않습니다.
  • 우리가 보관하는 비밀은 API 키와 웹훅 서명 키 둘뿐이며, 전부 Edge Function secret에만 있습니다. 관리자 콘솔(Vercel)에는 새 환경 변수가 없습니다.
  • 제공자 차이는 _shared/email/resend.ts 어댑터 한 파일에 가둬 Postmark 등을 나중에 추가할 수 있습니다.
1단계

MX를 바꾸지 않고 시작합니다. 기존 contact@ 메일함의 자동 전달 규칙으로 제공자 수신 주소에 복사본을 보냅니다. 메일함은 그대로 백업이 되고, 되돌리기는 규칙 삭제 한 번입니다. 안정화 뒤 수신 전용 서브도메인(in.글자월드.co.kr)의 MX만 Resend로 둡니다.

발신 · 스레딩 — email-outbound

콘솔 답신 → 저장(queued) → 함수 호출 → Resend 발송 → 상태 이벤트

sequenceDiagram
    actor OP as 운영자
    participant AC as replyToInquiryAction
    participant DB as inquiry_replies
    participant OF as email-outbound
    participant RS as Resend
    actor U as 사용자
    OP->>AC: 답신 제출 (source = email)
    AC->>AC: requirePermission('inquiries','write')
    AC->>DB: insert direction=outbound, delivery_status=queued
    AC->>OF: POST { replyId } + 운영자 JWT
    OF->>OF: getUser() · profiles.role = admin 확인
    alt secret 없음
        OF-->>AC: 503 not_configured
        AC-->>OP: "이메일 발송 설정이 아직 없습니다. 답신은 저장되었고…"
    else 설정됨
        OF->>RS: POST /emails (from EMAIL_FROM · reply_to reply+key@ · In-Reply-To/References · Idempotency-Key)
        RS-->>OF: { id }
        OF->>DB: email_message_id = id, delivery_status = sent
        AC-->>OP: 토스트 · 스레드에 "보낸 답신 · 발송됨"
        RS-->>U: 답신 메일
        RS-->>OF: email.delivered / bounced (웹훅 → email-inbound)
    end
    U->>RS: 답장 (To: reply+key@)
    RS->>OF: email.received → email-inbound 가 스레드에 "받은 메일" 추가
  • 제목은 Re: <원제목> [문의 #<짧은 id>]. 본문은 답신 내용 + 서명 푸터.
  • 발송 실패는 스레드에 보낸 답신 · 실패 칩과 다시 보내기(resendInquiryEmailAction)로 보입니다. 답신은 항상 저장되어 있으므로 설정 뒤에도 보낼 수 있습니다.
  • 감사 로그: inquiry.email.reply · inquiry.email.resend.

관리자 콘솔 변경

사이드바
고객지원 › 1:1 문의(?source=web) · 이메일 문의(?source=email) · FAQ. 쿼리를 인식하는 활성 판정(isPathActive · navBreadcrumb).
목록 InquiryTable · InquiryFilters
출처 필터(전체/웹/이메일), 출처 뱃지, 이메일 행은 계정 칸에 발신자 주소, SPF/DKIM/DMARC 중 하나라도 fail이면 "인증 실패" 경고 뱃지. 검색은 발신자 주소도 대상.
상세 InquiryEmailMeta
From(이름·주소) · Message-ID · 수신 시각 · SPF/DKIM/DMARC 칩. 계정 ID·개인정보 동의 행은 숨김.
스레드 InquiryEmailThreadItem
받은 메일 왼쪽 · 보낸 답신 오른쪽(강조). 발송 상태 칩과 실패 시 다시 보내기(InquiryResendButton).
답신 폼
버튼 "이메일로 답신 보내기", 힌트 "사용자의 메일 주소로 발송됩니다. 계정 정보나 개인정보는 적지 마세요." 2,000자 카운터 유지.
권한 · 문구
모듈 inquiries(read/write). 오류 문구는 개발자 가이드 §7 규약(actionFailure, "…하지 못했습니다 + 다음 행동"). 이메일 문의에는 접수 취소가 없습니다.

활성화 체크리스트

docs/admin/EMAIL-INQUIRY-ACTIVATION.md · 메일 주소와 Resend 계정이 준비된 뒤

  1. 결정 — 발신 주소(제안 support@글자월드.co.kr), 회신 도메인(in.글자월드.co.kr), 접수 확인 메일 on/off, 방침 개정. IDN 도메인은 DNS·제공자 화면에서 puny 코드(xn--bj0b33kj0qqva.co.kr)로 보입니다.
  2. 메일함 — 발신 주소 메일함(또는 별칭) 생성. 일부 메일 클라이언트는 Reply-To 대신 From으로 답장하므로 받을 수 있는 주소여야 합니다. 기존 contact@는 그대로.
  3. Resend 도메인 인증 — Domains › Add Domain → Records 탭의 DKIM·SPF(+Return-Path MX)·DMARC 레코드를 DNS에 그대로 추가 → Verified.
  4. 수신 — Emails › Receiving. 1단계 테스트는 계정에 주어지는 <id>.resend.app 주소로 충분. 자체 도메인은 in. 서브도메인에만 MX 추가(루트 MX는 건드리지 않음).
  5. 웹훅 — Endpoint https://zafouiovmsfebfkjuyos.supabase.co/functions/v1/email-inbound, 이벤트 email.received + email.sent·delivered·bounced·failed·complained. Signing Secret(whsec_…)과 발신+수신 읽기 권한 API 키(re_…) 복사.
  6. secret 설정(저장소 루트, 재배포 불필요) 
    supabase secrets set \
  RESEND_API_KEY='re_…' \
  RESEND_WEBHOOK_SECRET='whsec_…' \
  EMAIL_FROM='글자월드 고객지원 <support@xn--bj0b33kj0qqva.co.kr>' \
  EMAIL_REPLY_DOMAIN='in.xn--bj0b33kj0qqva.co.kr' \
  EMAIL_INQUIRY_ACK='on' \
  CLIENT_SITE_URL='https://maple-web-sigma.vercel.app'
  7. 자동 전달 — contact@ 메일함에서 Resend 수신 주소로 전달 규칙 추가("받은편지함에 복사본 유지"). Google Workspace의 전달 확인 메일은 Resend 대시보드 Receiving에서 코드 확인.
  8. 왕복 테스트 — 외부 메일 발송(PNG 1개 첨부) → 1분 내 콘솔 접수 대기 확인(From·Message-ID·인증 칩·첨부) → 접수 확인 메일 수신 → 콘솔 답신 → 메일 수신(From·Reply-To 확인) → 답장 → 스레드에 받은 메일 + 상태 처리 중 → 존재하지 않는 주소로 답신해 실패 칩·다시 보내기 확인.
secret필수뜻
RESEND_API_KEY예수신 본문 조회 + 발송. 없으면 수신 503(재시도), 발송 503 not_configured
RESEND_WEBHOOK_SECRET예Svix 서명 키. 없으면 수신 함수는 모든 요청을 503으로 거절
EMAIL_FROM예답신·접수 확인 메일의 From. 인증된 도메인
EMAIL_REPLY_DOMAIN권장reply+<key>@<값>. 비우면 회신 스레딩은 In-Reply-To에만 의존
EMAIL_INQUIRY_ACK선택on이면 접수 확인 메일(24시간 1회). 기본 꺼짐
CLIENT_SITE_URL선택접수 확인 메일의 방침 링크 기준 주소
확인

안 뜨면 Resend Webhooks › Attempts의 응답 코드를 봅니다. 401 서명 키 불일치 · 503 secret 누락 · 500 DB 오류(Supabase Edge Functions › Logs).

근거 · 가정 · 후속

Resend 공식 문서에서 확인한 것

  • 수신 이벤트 email.received의 data에는 메타데이터만 있고 본문·헤더는 GET /emails/receiving/{email_id}로 읽는다. 첨부는 …/attachments의 만료되는 download_url.
  • 서명 헤더 svix-id·svix-timestamp·svix-signature, HMAC-SHA256(whsec_ 뒤 base64 키, id.timestamp.body).
  • 발송 POST /emails: reply_to, headers(In-Reply-To·References), Idempotency-Key, 동기 응답 { id }. User-Agent 없으면 403.
  • 웹훅은 at-least-once, 재시도 5초·5분·30분·2시간·5시간·10시간.

문서에 없어 관용적으로 처리한 것

  • SPF/DKIM/DMARC 필드 — Authentication-Results 헤더에서 읽고, 제공자 필드가 있으면 우선. 없으면 뱃지 없음.
  • 발송 응답 id와 RFC Message-ID의 관계 — 답신 행에는 발송 id를 저장. 회신 스레딩은 reply+key가 1차, In-Reply-To 매칭은 세 가지 꼴을 모두 시도.
  • 웹훅에 본문이 인라인으로 실리면 API 조회 없이 사용(타 제공자 대비).

후속 과제

  • 실제 메일 왕복 검증(활성화 후 §09-8).
  • 개인정보처리방침 개정본 발행(이메일 문의 수집 항목·보유 기간).
  • 2단계: 안정화 뒤 수신 서브도메인 MX 이전, Postmark 등 어댑터 추가 여부.
