New Feature · 회원

회원 탈퇴 라이프사이클

회원 탈퇴는 두 단계 소프트 삭제입니다. 탈퇴 요청은 profiles.deleted_at 을 찍을 뿐이고, 90일이 지나야 개인정보가 실제로 사라집니다(purged_at). 프로필 행은 파기 후에도 남습니다 — 글·댓글의 author_id 가 살아 있어야 게시판이 그대로이기 때문입니다.

01

개요 · 결정 사항

오너 피드백 9건을 "탈퇴 기능 + 그 기능이 제재·게시글·재가입과 맞물리는 규칙"으로 정리한 결과입니다. 아래 8개 결정이 코드의 어디에 박혀 있는지가 이 문서의 골자입니다.

#결정구현
190일 보존 후 파기WITHDRAWAL_RETENTION_DAYS = 90(lib/auth/lifecycle.ts) · PURGE_RETENTION_DAYS = 90(admin/lib/validation/member-status.ts) · purge_withdrawn_profiles(p_cutoff interval default interval '90 days')
2탈퇴 대기 중에는 기존 닉네임 그대로파기 전에는 posts/comments.author_name 스냅샷을 건드리지 않습니다. 화면은 평소처럼 maskNickname() 결과를 그립니다
3파기 후에는 탈퇴한 회원#xxxxxxxxDB 는 '탈퇴한 회원#' || left(id::text, 8) 을 저장하고, 사용자 사이트는 접두사를 보고 고정 문구 탈퇴한 회원 으로 그립니다(lib/utils/author-display.ts). 관리자 콘솔은 저장값을 그대로 보여 줍니다 — 목록에서 여러 파기 계정을 구분해야 하기 때문입니다
4글·댓글은 유지profiles 행을 지우지 않고 익명화합니다. profiles.id → auth.users FK 를 걷어 내 auth 계정만 지워도 행이 남습니다
5제재는 탈퇴해도 유지, 파기 시 소멸탈퇴는 suspended_until 을 건드리지 않습니다. 파기 함수가 suspended_until·suspension_reason 을 비웁니다(식별 근거가 사라지므로)
690일 뒤 재가입은 새 계정 — 제재 미적용파기 시 auth.users 가 삭제되어 다시 로그인하면 handle_new_user() 가 새 프로필을 만듭니다. 옛 익명화 행과는 무관합니다
7월드 연동 필수 글쓰기는 플래그로 준비만, 기본 OFFFEATURES.postingRequiresMswLink ← NEXT_PUBLIC_FEATURE_POSTING_REQUIRES_MSW === 'true'
8월드 UID · 프로필 코드 유니크profiles_msw_uid_key · profiles_msw_profile_code_key(lower(msw_profile_code)). 둘 다 부분 유니크 인덱스
해석

"아이디 중복 불가" — 서비스에 별도 아이디가 없습니다(간편로그인만 씁니다). 닉네임은 이미 lower(nickname) 유니크였고, 이번에 월드 UID·프로필 코드에 유니크를 걸어 "같은 월드 계정을 두 프로필에 연결"하는 것을 막았습니다. 제재 회피를 막는 실질적 장치가 이것입니다.

주의

다른 간편로그인 계정으로 새로 가입하는 것은 지금도 막을 수단이 없습니다(이메일이 다르면 다른 사람입니다). 이 경로의 제재 회피는 월드 UID 유니크로만 막힙니다.

3.1 컬럼 · 인덱스

alter table public.profiles
  add column if not exists deleted_at timestamptz,
  add column if not exists purged_at  timestamptz;

-- 파기 배치가 "deleted_at <= 기준 시각 and purged_at is null" 로 훑는다.
create index if not exists profiles_deleted_at_idx
  on public.profiles (deleted_at) where deleted_at is not null;

create unique index if not exists profiles_msw_uid_key
  on public.profiles (msw_uid) where msw_uid is not null;

create unique index if not exists profiles_msw_profile_code_key
  on public.profiles (lower(msw_profile_code)) where msw_profile_code is not null;

프로필 코드는 저장 전에 소문자로 정규화되지만(lib/validation/auth.ts), DB 를 직접 고친 값까지 막으려고 lower() 로 겁니다. 적용 시점(2026-09-09) 중복 점검 결과 0건.

3.2 auth.users FK 제거 — 왜

alter table public.profiles drop constraint if exists profiles_id_fkey;

파기 순서는 프로필 익명화 → auth.users 삭제입니다. 기존 on delete cascade 가 남아 있으면 auth 삭제 순간 익명화된 프로필까지 사라지고, 글·댓글의 author_id 가 null 로 비워져 "게시판에는 영향이 없다"는 약속이 깨집니다.

FK 를 다시 걸지 않습니다. 프로필을 만드는 경로는 handle_new_user() 트리거(auth.users AFTER INSERT) 하나뿐이라, auth 없는 프로필은 파기 배치에서만 생기고 그것이 의도한 상태입니다.

3.3 is_withdrawn() 과 RLS

create or replace function public.is_withdrawn()
returns boolean language sql stable security invoker set search_path = public
as $$
  select exists (
    select 1 from public.profiles
    where id = (select auth.uid()) and deleted_at is not null
  );
$$;

revoke all on function public.is_withdrawn() from public, anon;
grant execute on function public.is_withdrawn() to authenticated, service_role;

is_suspended() 와 같은 구조입니다(SECURITY INVOKER · 자기 행만 읽습니다). not public.is_withdrawn() 이 추가된 정책은 8개입니다.

3.4 guard_profile_role() — 상태 컬럼 잠금

SECURITY INVOKER 여야 합니다. 순서대로 판정합니다.

  1. current_user 가 postgres · supabase_admin · service_role 이면 그대로 통과합니다.
  2. new.purged_at := old.purged_at — 관리자를 포함해 누구도 직접 못 씁니다. 파기 함수(SECURITY DEFINER, 소유자 postgres)와 서비스 롤만 1번 분기로 통과합니다.
  3. is_admin() 이면 슈퍼어드민이 아닐 때 role · admin_role_id 만 되돌리고 반환합니다. 즉 관리자는 다른 회원의 deleted_at 을 쓸 수 있습니다(강제 탈퇴의 근거).
  4. 일반 사용자는 role · admin_role_id · id · created_at · email · provider · provider_id · suspended_until · suspension_reason 가 전부 old 로 되돌아갑니다.
  5. 일반 사용자의 deleted_at 변경은 두 가지뿐입니다. null 로 만들기(복구) — 단 old.purged_at 이 있으면 무시합니다. 값 채우기(탈퇴) — 값이 무엇이든 now() 로 고정합니다. 과거 시각을 넣어 파기를 앞당기거나 먼 미래를 넣어 영원히 보존시키는 요청이 통하지 않습니다.

returns setof uuid · SECURITY DEFINER · 실행 권한은 service_role 뿐입니다. 대상은 deleted_at is not null and deleted_at <= now() - p_cutoff and purged_at is null, order by deleted_at, for update skip locked.

4.2 스케줄

비밀값은 마이그레이션 파일에 적지 않습니다. pg_cron 이 Vault 의 purge_withdrawn_cron_secret 을 읽어 헤더에 싣고, 함수는 자기 secret CRON_SECRET 과 비교합니다. UTC 18:00 = KST 03:00.

select cron.schedule(
  'purge-withdrawn-daily',
  '0 18 * * *',
  $job$
    select net.http_post(
      url := 'https://zafouiovmsfebfkjuyos.supabase.co/functions/v1/purge-withdrawn',
      headers := jsonb_build_object(
        'Content-Type', 'application/json',
        'x-cron-secret', (
          select decrypted_secret from vault.decrypted_secrets
          where name = 'purge_withdrawn_cron_secret' limit 1
        )
      ),
      body := '{}'::jsonb,
      timeout_milliseconds := 30000
    );
  $job$
);

등록 확인과 수동 실행:

select jobname, schedule, active from cron.job;

curl -X POST https://zafouiovmsfebfkjuyos.supabase.co/functions/v1/purge-withdrawn \
  -H 'Content-Type: application/json' \
  -H "x-cron-secret: $CRON_SECRET" \
  -d '{}'
미완

마이그레이션 8절의 DO 블록은 pg_cron 과 pg_net 이 둘 다 켜져 있을 때만 스케줄을 만듭니다. 적용 시점(2026-09-09) 프로젝트에는 두 확장이 없어 raise notice 만 남기고 지나갔습니다. 지금은 자동 파기가 돌지 않습니다. 확장을 켠 뒤 위 cron.schedule 을 SQL 편집기에서 그대로 실행하세요(같은 이름이면 갱신됩니다).

5.1 탈퇴

app/(auth)/account/page.tsx · components/auth/WithdrawAccountButton.tsx · lib/actions/account-actions.ts

  • 진입은 /account 맨 아래 "회원 탈퇴" 섹션 — 되돌리기 어려운 조작이라 로그아웃과도 떨어진 자리에 둡니다.
  • 확인 모달 3요소는 lib/auth/lifecycle.ts 의 상수입니다. WITHDRAW_DIALOG_TITLE("회원 탈퇴") · WITHDRAW_DIALOG_DESCRIPTION(90일 보존 · 파기 항목 · 글은 남고 "탈퇴한 회원" 표시 · 제재 유지) · 취소 + 위험 버튼.
  • withdrawAccountAction 은 세션 클라이언트로 자기 행의 deleted_at 만 씁니다. 허용 범위는 DB 가 정합니다(profiles_update_self + guard_profile_role()).
  • 갱신 뒤 .select('deleted_at').maybeSingle() 로 되읽습니다 — 정책에 걸려 0행이 바뀌어도 PostgREST 는 오류를 내지 않기 때문입니다.
  • 실패 문구는 탈퇴를 처리하지 못했습니다. 계정은 그대로입니다. 다시 시도해 주세요.
  • 성공하면 signOut() 후 /?notice=withdrawn 으로 리다이렉트하고, 홈이 WITHDRAWN_NOTICE_MESSAGE 를 한 번 보여 줍니다.

5.2 프록시 게이트

proxy.ts — Next.js 16 에서 middleware.ts 를 대체합니다

상수경로동작
WITHDRAWN_READ_PREFIXES/community/write · /account · /auth/onboarding · /support/inquiriesGET·HEAD → 302 /auth/restore?next=<원래 경로+쿼리>
WITHDRAWN_MUTATION_PREFIXES/community · /support · /account · /auth/onboarding비-GET → 403 {"error":"account_withdrawn","restorePath":"/auth/restore"}
  • /auth/restore 자체와 그 액션은 게이트에서 제외됩니다(가야 하는 곳이므로).
  • 프로필 조회는 로그인 상태 + 게이트 대상 경로일 때만 한 번 일어납니다. 모든 요청마다 DB 를 때리지 않습니다.
  • 리다이렉트에는 updateSession() 이 심은 갱신 쿠키를 옮겨 싣습니다(redirectWithSession). 안 그러면 리프레시 토큰이 유실돼 임의 로그아웃이 납니다.
  • 조회 실패는 "정상 회원"으로 봅니다(오탐 차단 방지). 쓰기는 RLS 가 최종적으로 막습니다.
  • 탈퇴 대기 중에도 공개 읽기는 그대로 열려 있습니다 — 홈 · 커뮤니티 목록/상세 · 뉴스 · 정책 문서 등.

5.3 복구

app/auth/restore/page.tsx · components/auth/RestoreAccountForm.tsx · components/layout/AuthMenu.tsx · MobileNav.tsx

  • 정상 회원이 주소로 직접 들어오면 next 로 그냥 보냅니다 — 물을 것이 없습니다.
  • 복구 가능하면 본문은 restoreNotice() — "탈퇴 후 N일이 지났습니다. 계속하면 계정이 복구됩니다. 이용 제한이 있었다면 그대로 적용됩니다."
  • 파기가 끝난 계정은 PURGED_ACCOUNT_MESSAGE 와 로그아웃 버튼만 남습니다(복구 버튼 없음).
  • 복구는 deleted_at 을 비우는 쓰기라 GET 링크가 아니라 폼 POST 여야 합니다(CSRF).
  • 헤더는 탈퇴 대기 계정에게 닉네임 메뉴 대신 "계정 복구" 버튼 하나만 보입니다. 근거는 getCurrentUser() 의 isWithdrawn.
  • 로그인 직후 목적지는 resolvePostAuthDestination() 하나가 소유합니다 — 탈퇴 > 온보딩 > next 순서. 인증 콜백(app/auth/callback/route.ts)과 스텁 로그인이 같은 함수를 씁니다.
순서

탈퇴 판정이 온보딩보다 먼저입니다. 탈퇴 대기 중인 사람에게 온보딩 폼을 먼저 보이면 "복구할지"를 묻기 전에 약관 동의를 다시 받는 셈이 됩니다.

6.2 회원 상세

  • MemberLifecycleCard — active 면 아예 그리지 않습니다. 탈퇴일 · 파기 예정일(D-nn, 위험 톤) · 파기일. 파기된 계정은 남은 일수를 적지 않습니다. 복구 이력은 적지 않습니다 — 복구는 deleted_at 을 비우는 것이라 별도 기록이 없고, 빈 칸을 두면 "복구한 적 없음"으로 읽힙니다. 감사 로그 member.restore 로 안내합니다.
  • MemberProfileCard — 파기된 계정은 이메일 · 공급자 ID · MSW UID · 프로필 코드 칸을 렌더하지 않습니다. 값이 빈 칸으로 남으면 "조회에 실패했나?"로 읽히고, 혹시 남은 값이 있다면 파기의 취지에 어긋납니다. 가입일 · 동의 시각 · 권한 등 나머지는 그대로입니다.
  • MemberActions — purged 면 조치 버튼을 전부 감춥니다(누를 것이 없습니다). active + 자기 자신이 아님 → 강제 탈퇴. withdrawn + 슈퍼어드민 + 자기 자신이 아님 → 개인정보 즉시 파기. 정지 · 정지 해제 · 닉네임 강제 변경은 탈퇴 대기 중에도 가능합니다.
  • 회원을 관리자로 승격하는 조작과 계정 삭제 버튼은 없습니다 — 삭제는 탈퇴 → 90일 → 파기 두 단계로만 일어납니다.

6.3 개인정보 즉시 파기 · 슈퍼어드민

admin/lib/actions/member-lifecycle-actions.ts · components/members/MemberPurgeDialog.tsx

  1. requireSuperAdmin(). 자기 자신은 막습니다 — 파기는 auth 계정까지 지우므로 진행하는 순간 세션이 끊기고 되돌릴 수단도 사라집니다.
  2. 상태 확인: purged → "이미 개인정보가 파기된 회원입니다." / active → "탈퇴하지 않은 회원입니다. 먼저 탈퇴 처리를 한 뒤에 파기할 수 있습니다."
  3. 배치 함수를 쓰지 않습니다. purge_withdrawn_profiles(p_cutoff) 도 Edge Function 도 대상 지정 인자가 없어(크론이 빈 본문으로 부릅니다) 한 명을 지우려고 부르면 기간이 지난 다른 회원까지 함께 파기됩니다. 그래서 서비스 롤로 한 명분만 같은 필드를 지웁니다.
  4. 순서: 프로필 익명화 → posts · comments 의 author_name 갱신 → auth.admin.deleteUser. 스냅샷 갱신 실패는 파기를 되돌리지 않습니다(개인정보는 이미 지워졌고, 되돌리면 더 나쁜 상태가 됩니다).
  5. auth 삭제 실패 시 purged_at 을 되돌립니다 — 로그인 수단이 남았는데 "파기됨"으로 표시되면 다음 배치가 이 회원을 건너뛰어 이메일이 영영 남습니다.
  6. 감사 로그 member.purge — 행위자는 슈퍼어드민, before 에 닉네임 · 이메일 · MSW 값 · deleted_at, after 에 { nickname, purged_at, immediate: true }.
  7. 사용자 사이트 캐시 태그 community-list 를 revalidate 합니다 — 작성자 표시 이름이 바뀌었기 때문입니다.

6.4 강제 탈퇴 · members:write

  • 자기 자신 금지. role = 'admin' 계정 금지(관리자는 /admins 에서 다룹니다 — 여기서 탈퇴시키면 역할은 남고 로그인만 막히는 어정쩡한 상태가 됩니다).
  • 이미 withdrawn · purged 면 거절합니다.
  • 제재는 건드리지 않습니다 — 복구하면 남은 제재가 그대로 적용되어야 "탈퇴로 제재를 피한다"는 길이 막힙니다.
  • 세션 클라이언트로 씁니다(서비스 롤 아님). profiles_update_admin 이 관리자에게 다른 회원의 UPDATE 를 열어 주고 guard_profile_role() 도 관리자 분기에서 deleted_at 을 잠그지 않습니다. 서비스 롤을 쓰면 DB 트리거가 남기는 member.withdraw 의 행위자가 null 이 되어 추적이 끊깁니다.
  • 결과적으로 감사 로그에 두 줄이 남습니다 — 트리거의 member.withdraw(행위자 = 관리자) + 액션의 member.force_withdraw.

E2E 실사 검증

배포된 purge-withdrawn 은 인증 없는 POST → 401 unauthorized, GET → 405 method_not_allowed 를 실제 호출로 확인했습니다. 브라우저 시나리오(스텁 로그인 + 원격 Supabase 서비스 롤)는 다음을 한 번에 확인합니다.

  1. 로그인 · 온보딩 → 검증용 글 1건 작성
  2. /account → 탈퇴 모달(제목 · 설명 문구 일치) → 탈퇴 → /?notice=withdrawn 안내 · 헤더가 로그인 상태로 되돌아감 · deleted_at 세팅 · 감사 로그 member.withdraw(행위자 = 본인)
  3. 같은 계정으로 재로그인 → /auth/restore 로 튕김. /community/write 직접 진입도 복구 화면으로. 헤더에 "계정 복구"
  4. 복구 → 마지막 next(/community/write)로 착지 · deleted_at 비워짐
  5. 다시 탈퇴 → purge_withdrawn_profiles('0 seconds') 로 즉시 파기 → 프로필 익명화 · posts.author_name 갱신 · 상세 화면 작성자 "탈퇴한 회원" · 감사 로그 member.purge
  6. auth.admin.deleteUser 뒤에도 프로필 행이 남는지(FK 제거 확인)
주의

로컬 재현은 서비스 롤 클라이언트로 rpc('purge_withdrawn_profiles', { p_cutoff: '0 seconds' }) 를 부르면 됩니다. 기준 기간이 지난 다른 계정도 함께 파기되므로 운영 DB 에서는 절대 쓰지 않습니다.

09

운영 체크리스트 · 주의사항

  1. cron 등록 — pg_cron · pg_net 확장을 켜고 §04-2 의 cron.schedule 을 실행한 뒤 select jobname, schedule, active from cron.job; 로 확인합니다. Vault 의 purge_withdrawn_cron_secret 과 함수 secret CRON_SECRET 이 같은 값이어야 합니다. 2026-09-09 운영자가 확장 활성화 후 등록을 마쳤습니다. 새 환경을 만들 때는 같은 절차를 반복합니다.
  2. 스텁 계정 정리 시 profiles 행도 함께 지웁니다. FK 를 걷어 냈으므로 auth.admin.deleteUser() 만으로는 프로필이 남습니다. supabase/README.md §"스텁 계정 정리"에 프로필 삭제 단계가 추가돼 있습니다.
  3. .env.example 에 NEXT_PUBLIC_FEATURE_POSTING_REQUIRES_MSW=false 가 있습니다. 플래그를 켜기로 하면 배포 환경 변수도 함께 추가합니다.
  4. 감사 로그는 append-only 입니다. 탈퇴 · 복구는 트리거가 남기므로 사용자 사이트 코드가 로그를 건너뛸 방법이 없습니다.
  5. 파기는 되돌릴 수 없습니다. 즉시 파기는 슈퍼어드민만, 자기 자신에게는 불가. 확인 모달이 "되돌릴 수 없습니다"와 "글 · 댓글은 남습니다"를 모두 적습니다 — 앞을 빼면 가볍게 누르고, 뒤를 빼면 게시판이 통째로 사라진다고 오해합니다.
  6. 이메일 중복 재가입 — 90일 안에 같은 간편로그인 계정이면 복구(상태값만 변경, 닉네임 · 월드 계정 · 제재 그대로). 다른 간편로그인 계정이면 새 회원(막을 수단 없음). 파기 후에는 auth.users 가 없으므로 handle_new_user() 가 새 프로필을 만들고 제재는 따라오지 않습니다.
  7. 배치는 여러 번 실행돼도 안전합니다 — 대상 조건에 purged_at is null 이 있고 익명화 결과는 멱등이며, for update skip locked 로 동시 실행도 서로 밟지 않습니다.
