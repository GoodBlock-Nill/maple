02

인증

원칙

  • 관리자 계정의 로그인 수단은 이메일 + 비밀번호 하나입니다. 간편로그인 버튼은 없앴습니다 (admin/app/(auth)/login/page.tsx, 2026-09-09 제품 결정).
  • 계정은 초대로만 만들어집니다(§04). 사용자 사이트 회원을 승격하는 화면은 없습니다.
  • 로그인에 성공해도 profiles.role !== 'admin'이면 세션을 남기지 않고 즉시 로그아웃합니다 (signInAction). 세션만 남기면 "로그인은 됐는데 모든 화면이 튕기는" 상태에 갇힙니다.
  • 아이디/비밀번호 중 어느 쪽이 틀렸는지 알리지 않습니다(계정 열거 차단).
  • 비밀번호는 10자 이상 72자 이하(ADMIN_PASSWORD_MIN_LENGTH · MAX_LENGTH, bcrypt가 73바이트째부터 버립니다).

세션 · 쿠키

admin/proxy.ts · admin/lib/supabase/middleware.ts · admin/lib/auth/session.ts

  • proxy.ts가 Next 16의 구 middleware.ts입니다. 세 가지를 합니다: 매 요청 세션 갱신(updateSession()), 미로그인 요청을 /login?next=…로(낙관적 검사), 30분 비활동 만료.
  • 검증은 getSession()이 아니라 getUser()입니다. getSession()은 쿠키의 JWT를 그대로 신뢰해 위조 쿠키를 통과시킵니다.
  • 리다이렉트를 만들 때 갱신된 인증 쿠키를 반드시 복사합니다(redirectWithSession). 빠뜨리면 리프레시 토큰이 저장되지 않아 임의로 로그아웃됩니다.
  • 30분 타이머는 admin_last_seen 쿠키입니다(INACTIVITY_LIMIT_MS). 쿠키가 없으면 만료로 보지 않습니다 — 로그인 직후 첫 요청에는 쿠키가 없기 때문입니다. 보안 경계가 아니라 편의 장치입니다.
  • 공개 경로 PUBLIC_PREFIXES: /login /forgot-password /reset-password /invite/accept /auth/callback. 정적 자산은 matcher에서 제외합니다.

비밀번호 재설정

  1. /forgot-password → requestPasswordResetAction → resetPasswordForEmail(redirectTo: {ADMIN_URL}/auth/callback?next=/reset-password)
  2. 성공/실패를 구분해 답하지 않습니다(계정 열거 차단). 실제 발송 실패는 서버 로그에만 남습니다.
  3. 링크가 세션을 만들면 /reset-password에서 setPasswordAction이 비밀번호를 바꿉니다. 세션이 없으면 "링크가 만료되었습니다"로 안내합니다.
  4. 같은 비밀번호(error.code === 'same_password')만 필드 오류로 되돌립니다.

개발용 로그인 미리 채움

ADMIN_LOGIN_PREFILL_EMAIL · ADMIN_LOGIN_PREFILL_PASSWORD가 있으면 로그인 칸이 미리 채워집니다.

주의

이 값은 공개 로그인 페이지의 HTML에 그대로 실립니다. 개발 기간에만 켜고, 운영 배포에서는 제거 대상입니다.

03

권한 체계(RBAC)

데이터 모델

supabase/migrations/20260909000200_admin_roles.sql

admin_roles
key는 ^[a-z][a-z0-9_]{1,30}$, 생성 후 불변. permissions는 { "<module>": "none"|"read"|"write" } jsonb. 시드: super_admin(전체 write, 시스템) · editor(예시).
profiles.role = 'admin'
콘솔에 들어올 수 있는가. RLS 전체가 쓰는 거친 문 is_admin()의 근거.
profiles.admin_role_id
무엇을 할 수 있는가. on delete set null. 비어 있으면 아무 모듈도 못 봅니다(닫힘 실패).
is_super_admin()
역할·관리자 관리의 판정. SECURITY DEFINER, search_path 고정.

가드 트리거 둘. guard_admin_roles()는 시스템 역할의 수정·삭제를 막고 key·is_system·created_at을 불변으로 만듭니다. guard_profile_role()은 SECURITY INVOKER여야 합니다 — DEFINER로 두면 current_user가 함수 소유자로 평가되어 가드가 통째로 사라집니다(20260908001000의 사고). 슈퍼어드민이 아닌 관리자는 role·admin_role_id를 바꿀 수 없습니다.

모듈 13개

admin/lib/auth/permissions.ts · ADMIN_MODULES

dashboard · news · community · reports · members · inquiries · faqs · gacha · rankings · settings · legal · admins · audit

  • 등급은 none < read < write. write는 read를 포함합니다.
  • 값이 없는 모듈은 none으로 읽습니다 — 닫힘 실패. 모듈을 새로 추가해도 기존 역할에서 자동으로 열리지 않습니다.
  • parsePermissions()는 모르는 키·값을 버립니다. 이 파일에는 server-only를 붙이지 않습니다 — 사이드바(클라이언트)가 같은 판정으로 메뉴를 감춰야 하기 때문입니다.

RLS는 모듈별 권한을 모릅니다. 정책에 역할을 녹이면 정책 수가 모듈 × 역할로 폭발하고, 역할을 추가할 때마다 마이그레이션이 필요해집니다. 그래서 DB는 "관리자인가"까지만 보고, 모듈별 read/write는 앱이 강제합니다.

신뢰 경계

모듈 권한만으로는 데이터가 보호되지 않습니다. 읽기 전용 역할의 계정도 anon 키 + 자기 세션으로 REST를 직접 부르면 관리자 테이블을 쓸 수 있습니다. 역할은 "운영자가 실수로 남의 영역을 건드리지 않게 하는 경계"이고, 신뢰 경계는 여전히 role='admin'입니다. 신뢰할 수 없는 사람에게는 관리자 계정을 주지 않습니다.

가드 (admin/lib/auth/require-admin.ts)실패 시쓰는 곳
requireAdmin()로그아웃 + /login(admin)/layout.tsx, 대시보드
requirePermission(module, level)/?error=forbidden각 페이지 · 쓰기 액션 첫 줄
requireAnyPermission(modules, level)/?error=forbidden신고 처리의 콘텐츠 숨김
requireSuperAdmin()/?error=forbidden/admins · 초대 · 삭제 · 역할

requireAdmin()만 로그아웃시키는 이유: 관리자가 아니면 계정 자체가 콘솔의 대상이 아닙니다. 모듈 권한 부족은 계정이 정상이고 이 화면만 닫힌 것이라 세션을 끊으면 쓸 수 있는 화면까지 잃습니다. 그래서 대시보드로 되돌리고 배너로 사유를 알립니다. 역할은 requireAdmin()이 프로필과 같은 질의로 읽습니다.

UI 게이팅

  • 사이드바(Sidebar.tsx)는 visibleNavItems(permissions)로 메뉴를 거릅니다. none인 모듈은 지웁니다. 하위가 전부 닫힌 부모는 사라지고, 첫 하위가 닫혔으면 부모 링크가 남아 있는 첫 하위로 옮겨 갑니다.
  • 쓰기 컨트롤: 페이지가 hasPermission(permissions, '<모듈>', 'write')를 canWrite로 내려 버튼·폼을 감춥니다. 값은 보여 주고 저장 수단만 없앱니다.
  • 이것은 편의이지 인가가 아닙니다. 인가는 페이지와 서버 액션이 합니다.

새 모듈을 추가할 때 체크리스트

  1. ADMIN_MODULES에 { key, label } 한 줄. 기존 역할에서는 자동으로 none.
  2. 시드 역할의 권한을 함께 갱신할지 결정. super_admin은 전체 write를 유지해야 합니다.
  3. admin/lib/nav.ts의 NAV_ITEMS에 항목 추가. 작성 화면은 level: 'write'.
  4. 페이지 첫 줄에 requirePermission('<모듈>', 'read'). 작성/편집 전용 화면은 'write'.
  5. 조회는 lib/data/<모듈>.ts(server-only + 세션 클라이언트), 변경은 lib/actions/<모듈>-actions.ts.
  6. 쓰기 액션 첫 줄은 항상 const actor = await requirePermission('<모듈>', 'write'). 서버 액션은 직접 POST로도 호출됩니다.
  7. 상태를 바꾸면 writeAuditLog(actor.id, …)(§06).
  8. 사용자 사이트에 보이는 변경이면 revalidateClient([...])(§05). 새 태그는 사용자 사이트 CACHE_TAGS에 먼저 넣고 CLIENT_CACHE_TAGS에 같은 값을 더합니다. 순서가 반대면 400.
  9. RLS 확인. 새 테이블은 revoke all … from anon, authenticated 뒤 필요한 grant를 명시 — 정책은 권한을 주지 않습니다.
  10. 목록은 Table + Pagination + table-query.ts. 정렬·페이지는 쿼리스트링에.
  11. 유닛 테스트 추가. 새 액션은 actions-no-raw-error.test.ts 규약을 지키는지 확인.

초대

순서

inviteUserByEmail()은 메일을 보내는 순간 auth.users 행을 만들고, 그 순간 handle_new_user()가 돕니다. 초대 행 insert가 먼저여야 트리거가 그 행을 찾습니다. 발송이 실패하면 반드시 초대 행을 revoked로 되돌립니다 — 남겨 두면 그 주소로 가입하는 누구나 관리자가 됩니다.

트리거의 승격 조건: lower(email) 일치 + status='pending' + expires_at 미경과. 여러 건이면 created_at 오름차순 첫 행. role은 raw_user_meta_data에서 절대 읽지 않습니다. 초대에 role_id가 비어 있으면 슈퍼어드민으로 떨어뜨리지 않고 권한 없는 관리자로 만듭니다(안전한 실패).

링크 착지 — /auth/callback

형태언제처리
?code=PKCEexchangeCodeForSession()
?token_hash=&type=메일 템플릿이 {{ .TokenHash }}verifyOtp() (허용 타입 5종)
#access_token=…암시적 흐름/auth/callback/complete가 브라우저에서 읽어 establishSessionAction으로 넘김

어느 경로든 세션이 생기면 rejectNonAdmin()이 profiles.role을 확인하고, 관리자가 아니면 signOut() 후 /login?error=not_admin으로 보냅니다. 초대 메일은 ?next=/invite/accept로 오며, 세션이 있으면 비밀번호 폼을, 없으면 "초대 재발송을 요청해 주세요" 안내를 그립니다.

재발송 · 취소 · 만료

  • 재발송: expires_at을 7일 뒤로 갱신한 뒤 같은 API를 다시 부릅니다. 링크만 새로 오고 허용 목록이 만료돼 있으면 트리거가 승격을 거르므로 둘을 함께 연장합니다.
  • 취소: status='revoked'. 행은 지우지 않습니다(admin_invites에 DELETE 정책이 없음).
  • 만료: INVITE_TTL_MS = 7일. Supabase 초대 링크의 수명(기본 24시간)과 다른 개념으로, "이 주소로 가입하면 관리자가 된다"는 근거의 수명입니다. 목록은 만료된 초대도 보여 줍니다 — 재발송 대상이기 때문입니다.
  • 같은 이메일 초대는 upsert가 아니라 조회 후 update/insert. 유니크 인덱스가 lower(email) 식이라 on conflict (email)과 맞지 않습니다.

삭제 = 비활성화

deleteAdminAction · admin/lib/actions/admin-actions.ts

  1. profiles.role = 'user', admin_role_id = null
  2. 그 이메일의 초대를 revoked로 — 같은 주소로 재가입해도 다시 관리자가 되지 않습니다
  3. 서비스 롤로 auth.admin.updateUserById(id, { ban_duration: '876600h' }) (100년; Supabase에 영구 차단 플래그가 없음)

계정 행을 지우지 않는 이유: 그 사람이 쓴 뉴스·답변의 작성자 참조가 끊깁니다. 3번이 없으면 role만 내려간 계정이 로그인은 계속 성공하고 화면에서만 튕깁니다. 3번이 실패해도 삭제를 되돌리지 않습니다(로그만).

NEXT_PUBLIC_SUPABASE_ANON_KEY클라이언트anon 키(RLS로 보호)
SUPABASE_SERVICE_ROLE_KEY서버 전용Auth Admin API 전용. 절대 커밋·클라이언트 노출 금지
NEXT_PUBLIC_CLIENT_SITE_URL클라이언트사용자 사이트 주소. "원문 보기" 링크
NEXT_PUBLIC_ADMIN_URL클라이언트관리자 자기 주소. 초대·재설정 메일의 redirectTo
CLIENT_SITE_URL서버 전용캐시 무효화를 보낼 주소. 로컬에서는 반드시 로컬 서버
REVALIDATE_SECRET서버 전용사용자 사이트의 같은 이름 변수와 동일한 값
ADMIN_BOOTSTRAP_EMAIL / _PASSWORD스크립트부트스트랩 전용. 운영 env에는 넣지 않음
ADMIN_LOGIN_PREFILL_EMAIL / _PASSWORD로컬 전용로그인 칸 미리 채움. 운영 설정 금지(HTML에 실림)

Supabase 값 3개와 REVALIDATE_SECRET은 루트 .env.local과 같은 값을 씁니다. requireEnv()는 안내와 함께 던지고, optionalEnv()는 빈 문자열을 "설정하지 않음"으로 봅니다.

첫 슈퍼어드민

ADMIN_BOOTSTRAP_EMAIL=... ADMIN_BOOTSTRAP_PASSWORD=... pnpm --filter @maple/admin bootstrap:admin
  1. admin_roles에서 super_admin id를 읽습니다(없으면 "마이그레이션을 먼저 적용하세요").
  2. admin_invites에 그 역할을 실은 초대 행을 만듭니다(expires_at = null) — 계정 생성보다 먼저.
  3. auth.admin.createUser({ email_confirm: true }) — 메일 확인 없이 바로 로그인.
  4. 이미 있는 계정이면 비밀번호만 재설정.
  5. profiles.role · admin_role_id가 슈퍼어드민인지 확인하고 아니면 보정.

알려진 제약 · 후속 과제

코드와 README에서 확인된 것만 적었습니다.

  1. 역할 변경은 다음 요청부터 적용됩니다. 권한은 요청마다 requireAdmin()이 읽으므로 이미 열린 화면은 그대로입니다.
  2. 마지막 로그인 시각은 표시하지 않습니다. auth.users에만 있어 서비스 롤 전수 조회가 필요합니다. 이력은 /audit가 더 정확합니다.
  3. 실제 초대 메일 E2E는 SMTP 연결 후에 가능합니다. admin.spec.ts는 화면과 버튼 존재까지만 확인합니다.
  4. 랭킹 스냅샷은 관리자가 적재하지 않습니다. 개발팀 연동이 rankings에 스냅샷 단위로 넣고, 관리자는 확인과 되돌리기만. 원자적 교체 RPC public.replace_ranking_snapshot(p_rank_type, p_rows jsonb)가 있으며 첫 줄에서 is_admin()을 확인하고 rank는 1..n 연속이어야 합니다.
  5. Legal 초안 삭제는 서버 액션만 있고 UI가 없습니다. deleteLegalDraftAction은 감사 로그까지 갖췼지만 호출 컴포넌트가 없습니다.
  6. 히어로 배너는 한 장만 노출됩니다. 슬라이더가 없어 목록 두 번째부터는 대기 상태입니다.
  7. admin_invites.token_hash는 비어 있습니다. 자체 초대 링크로 전환할 때를 위한 자리입니다.
  8. 역할이 비어 있는 관리자는 아무 모듈도 보지 못합니다(닫힘 실패). 그래서 멤버가 있는 역할의 삭제를 막습니다.
  9. docs/admin/PLAN.md §5.1과 client-revalidate.spec.ts 주석은 revalidateTag(tag,'max') 기준으로 쓰여 있으나 현재 코드는 { expire: 0 }입니다.
