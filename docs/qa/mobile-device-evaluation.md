# 실기기 모바일 점검 (2026-09-09)

오너 제보: **"버튼도 잘 안 눌리고, 헤더의 메뉴 버튼을 눌러도 올바르게 동작하지 않는다"**
(실제 iPhone · Galaxy). 기존 검증은 Chromium 기기 에뮬레이션뿐이었고, 거기서는
재현되지 않았다.

측정 환경 — Playwright WebKit 2359(`iPhone 14` / `iPhone 12`, 390·375px)와
Chromium(`Galaxy S9+` / `Pixel 7`, 320·412px), `hasTouch: true`, `page.touchscreen`
원시 터치 시퀀스. 대상은 프로덕션(`https://maple-web-sigma.vercel.app`)과 로컬
`:3000` 양쪽.

## 1. 근본 원인

### 1-1. 드로어가 헤더 안에 갇힘 — **WebKit 전용** (치명)

`.glass`(헤더 바)에 `backdrop-filter: blur(7.5px)` 가 걸려 있다. 명세상
`backdrop-filter` 는 `position: fixed` 자손의 **containing block** 이 되는데,
**WebKit 만 이를 구현**하고 Blink 는 하지 않는다. 드로어 마크업이 헤더 안에
있었으므로 iOS Safari 에서만 패널이 헤더 크기로 잘렸다.

실측(WebKit · iPhone 14 · 390×664, 수정 전):

| 대상                              | 기대           | 실제(WebKit)                    | 실제(Chrome) |
| --------------------------------- | -------------- | ------------------------------- | ------------ |
| `#mobile-nav-panel` 크기          | 335×664        | **306×74**                      | 275×658      |
| `offsetParent`                    | `null`(뷰포트) | **`HEADER`**                    | `null`       |
| "뉴스" 링크 좌표의 실제 히트 요소 | 그 링크        | **다른 버튼(`A.rounded-pill`)** | 그 링크      |

즉 메뉴를 열면 항목이 화면에 제대로 그려지지 않고, 항목이 있어야 할 자리를
누르면 **엉뚱한 버튼이 눌렸다**. 제보 문구와 정확히 일치한다.
→ **수정 완료(c9e6d8d, 다른 작업자)**: 오버레이·패널을 `createPortal` 로
`document.body` 에 붙였다. 회귀 방지 테스트는 아래 4절.

### 1-2. 폰트 2.86MB 를 모든 페이지가 강제로 내려받음 (높음)

`next/font/local` 은 선언한 **모든 파일**을 `<link rel="preload" as="font">` 로
박는다. 프로덕션 `<head>` 에 폰트 preload 링크가 **12개** 있었다.

| 폰트                             | 크기        | 실제 쓰임                            |
| -------------------------------- | ----------- | ------------------------------------ |
| PretendardVariable.woff2         | **2,010KB** | 모든 한글                            |
| MaplestoryOTF Light+Bold         | **619KB**   | `/소개` 텍스트 **두 줄**             |
| Switzer OTF 8벌(이탤릭 4벌 포함) | 183KB       | 라틴 본문(이탤릭은 에디터 `<em>` 뿐) |
| Inter(라틴 서브셋)               | 48KB        | 헤더 GNB·버튼                        |

체감 경로: 셀룰러에서 2.86MB 가 먼저 큐를 채운다 → JS 청크가 밀린다 →
**하이드레이션 전에 누른 탭은 핸들러가 없어 그대로 버려진다.** 사용자에게는
"눌러도 아무 일도 안 일어남"으로 보인다. (Playwright 스펙 작성 중에도 같은
경합이 그대로 재현됐다 — `domcontentloaded` 직후 햄버거를 누르면 열리지 않는다.)

### 1-3. `touch-action` 이 전부 기본값 `auto` (중간)

조사한 9개 페이지의 **모든** 인터랙티브 요소가 `touch-action: auto` 였다.
브라우저는 더블탭 확대 가능성 때문에 첫 탭 판정을 최대 300ms 미룬다. 그 사이
손가락이 조금만 움직여도 합성 `click` 이 취소된다 — "한 번에 안 눌린다"의 전형.

### 1-4. 탭 대상이 손가락보다 작음 (중간)

Apple HIG 44×44pt / Android 48dp 기준 미달 목록(390px 기준 실측):

| 요소                       | 크기              | 위치                          |
| -------------------------- | ----------------- | ----------------------------- |
| 푸터 메뉴·정책 링크        | **28×20 ~ 55×20** | 전 페이지 푸터                |
| SNS 아이콘                 | **32×32**         | 전 페이지 푸터                |
| 정렬 트리거("최신순")      | **85×26**         | `/news` `/community` `/guide` |
| 헤더 로고                  | 99×**36**         | 전 페이지                     |
| 헤더 "로그인"(Button `sm`) | 75×**40**         | 전 페이지                     |
| 검색 입력                  | 299×**43**        | 목록 페이지                   |
| 고객지원 select·input      | 316×**40**        | `/support`                    |

## 3. 개선 전/후 수치

측정: Chrome + `devices['Pixel 7']`, CPU 4× 스로틀, 네트워크 4Mbps/150ms RTT.
"전"은 프로덕션, "후"는 로컬 `:3000`(개발 서버)이다 — **폰트 파이프라인 비교만
직접 비교로 유효**하고, 총 전송량에는 개발/프로덕션 번들 차이가 섞여 있다.

### 폰트 전송량 (직접 비교, 확정치)

| 페이지       | 전                   | 후                 | 절감 |
| ------------ | -------------------- | ------------------ | ---- |
| `/`          | **2,860KB** (12파일) | **399KB** (16파일) | −86% |
| `/community` | **2,860KB**          | **487KB**          | −83% |
| `/about`     | **3,072KB**          | **928KB**          | −70% |

내역(`/`): Pretendard 2,010KB → **179KB**(실제 쓰인 unicode-range 조각 7개만),
Maplestory 619KB → **0KB**(`/소개` 에서만 341KB), Switzer 183KB → 172KB(변동 없음).

### 폰트 준비 시간 (`document.fonts.ready`)

| 페이지       | 전          | 후                 |
| ------------ | ----------- | ------------------ |
| `/`          | **7,821ms** | **1,984ms** (−75%) |
| `/community` | **7,227ms** | **1,866ms** (−74%) |

### 참고: 프로덕션 CPU 지표 (수정 전, 4× 스로틀·비스로틀 네트워크)

`/` LCP 876ms · TBT 30ms · long task 1개 / `/community` LCP 1,516ms · TBT 21ms.
→ **CPU 는 원래 여유가 있었다.** 병목은 대역폭이었고, 그래서 회선이 느린
실기기에서만 증상이 났다(사무실 Wi‑Fi 에뮬레이션에서 안 보인 이유).

### GIF 반복 렌더 비용 — 원인 아님

| 페이지       | DOM 내 GIF | 첫 화면에 보이는 GIF | 보이는 애니메이션 면적    | 유휴 6초 CPU(4×) |
| ------------ | ---------- | -------------------- | ------------------------- | ---------------- |
| `/`          | 8          | 5                    | 17,904px² (뷰포트의 0.5%) | Task 0.002s      |
| `/community` | 2          | 0                    | 0                         | Task 0.006s      |
| `/about`     | 10         | 0                    | 0                         | Task 0.001s      |

`image-rendering: pixelated` 가 걸린 것은 `/` 기준 3개뿐이고 표시 크기가 작다.
**GIF 를 멈추거나 줄일 이유는 측정상 없다** — 시안이 요구하는 애니메이션을 그대로 둔다.
다만 히어로 GIF 4종은 `priority` 로 preload 되며 합계 **259KB**(`pixchar-left.gif`
혼자 146KB)다. 첫 화면에 실제로 보이므로 preload 자체는 타당하지만, 용량을 줄이려면
GIF 자체를 최적화하는 편이 낫다(코드 변경 아님).

> 한계: 헤드리스/백그라운드 창에서는 브라우저가 GIF 프레임 진행을 스로틀해
> `Frames=0` 이 나온다. 위 CPU 수치는 **상한이 아니라 하한**이다. 다만 애니메이션
> 면적이 뷰포트의 0.5% 라 실기기에서도 무시할 수준으로 본다.

## 5. 실기기 없이는 확인 못 한 것

에뮬레이션으로는 여기까지가 한계다. 아래는 **실제 폰에서만** 확정할 수 있다.

1. **iOS 버전별 `inert`** — 드로어 닫힘 상태는 `inert` 와 `invisible` 을 함께
   쓰지만, iOS 15.5 미만에는 `inert` 가 없다. `visibility: hidden` 이 있어 탭은
   막히지만, 실기기 확인 전에는 100% 라고 말할 수 없다.
2. **주소창 표시/숨김에 따른 뷰포트 변화** — Playwright 뷰포트는 고정이라
   스크롤 중 주소창이 접히며 생기는 레이아웃 변화를 재현하지 못한다.
3. **Samsung Internet** — 엔진은 Blink지만 확대·글꼴 크기 기본값이 다르다.
   Chromium 에뮬레이션으로 대체 검증만 했다.
4. **실제 셀룰러(LTE/5G)** — 위 수치는 스로틀 근사값이다.
5. **GIF 애니메이션의 실제 배터리·CPU 비용** — 4절 한계 참고.
6. **손가락 오탭률** — 8번(부유 헤더가 상단 14% 를 덮음)이 실제로 얼마나
   거슬리는지는 사람이 써 봐야 안다.

### 아직 안 고친 것(예상되는 잔여 불편)
